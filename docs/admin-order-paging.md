# 관리자 주문 목록 페이지 나누기

`GET /api/admin/orders`는 두 방식을 모두 지원합니다.
정렬은 같습니다: 최신순, 같은 시각이면 주문 id가 큰 순.

| | 번호 방식 | 커서 방식 |
| --- | --- | --- |
| 요청 | `?page=3` | `?cursor=<앞 응답의 nextCursor>` |
| 화면에서 | 1 2 3 … 38 다음 | 이전 · 다음 10건 |
| 응답의 `total`·`pageCount` | 있다 | 있다(같은 값) |
| 원하는 쪽으로 바로 가기 | 된다 | 안 된다(앞에서부터 이어 받는다) |
| 보는 동안 주문이 새로 들어오면 | 밀려서 같은 주문이 다음 쪽에 또 나올 수 있다 | 이어서 받으므로 겹치거나 빠지지 않는다 |
| 뒤쪽 페이지의 목록 조회 비용 | 건너뛸 줄이 늘어난다 | 일정하다 |

`total`과 `pageCount`는 두 방식이 같습니다.
상태 칩 개수를 보이려면 조건에 맞는 주문을 어차피 세어야 해서, 서버가 목록 조회와 별도로 한 번 세어 주기 때문입니다.
커서 방식이 포기하는 것은 총 페이지 수를 아는 것이 아니라 "원하는 쪽으로 바로 가기"이고, 얻는 것은 목록 조회 비용이 일정하고 새 주문에 밀리지 않는 것입니다.
다만 이 세는 일은 주문이 많을수록 늘어나므로, 칩 개수가 필요 없는 목록이라면 커서 방식에서는 세기를 빼는 것이 더 맞습니다.

화면은 번호 방식을 씁니다.
운영자가 "3쪽"처럼 자리를 기억하고, 상태 칩 개수로 전체 규모를 함께 보기 때문입니다.
`orders:simulate`처럼 주문이 계속 들어오는 목록을 끝까지 훑어야 한다면 커서 방식이 맞습니다.

커서는 `주문 시각|주문 id`를 base64url로 감싼 값입니다.
화면은 뜻을 몰라도 그대로 돌려보내면 됩니다.
형식이 틀린 커서(칸이 둘이 아니거나, 시각·id가 올바르지 않은 값)는 400 `VALIDATION_FAILED`입니다.
